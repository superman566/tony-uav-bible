# 如何使用 YOLO

## Part 1：认识 YOLO26 模型家族

**一句话理解**：YOLO26 不是单一个模型，而是同一套骨干网络（Backbone）配上不同的"检测头"（Head），拼出一整个任务矩阵——横向是模型大小档位，纵向是要做的任务，两个维度组合起来一共 35 个可下载的权重文件。

![YOLO26 模型家族：任务 × 规模矩阵](/images/yolo-models.png)

### 横向：五档模型大小

文件名最后那个字母（比如 `yolo26n.pt` 里的 `n`）决定模型规模：

| 档位 | 全称 | 特点 |
|-|-|-|
| n | nano | 参数最少、推理最快，精度相对最低——机载算力有限的场景优先选它 |
| s | small | 比 n 稍大 |
| m | medium | 速度和精度比较均衡 |
| l | large | 参数多、精度高，速度变慢 |
| x | extra-large | 参数最多、精度最高，也最吃算力 |

字母越靠后模型越大，是"精度换速度"这条曲线上的五个采样点，不是五个互相独立的模型。

### 纵向：七种任务变体

同一个骨干网络换一个检测头就能做不同任务，文件名里加个后缀区分：

| 变体 | 任务 | 输出的是什么 |
|-|-|-|
| `yolo26n.pt`（无后缀） | Detection（目标检测） | 类别 + 矩形边界框——就是 [目标检测基础](/ai-yolo/object-detection-basics) 里一直讲的那种输出 |
| `-seg` | Instance Segmentation（实例分割） | 除了框，还给每个物体一个像素级的轮廓遮罩（Mask），能分清"这堆像素属于哪一个具体的人" |
| `-sem` | Semantic Segmentation（语义分割） | 也是像素级，但只分类别不分个体——"哪些像素是人"，不管这是几个人 |
| `-depth` | Depth Estimation（深度估计） | 每个像素输出一个"离摄像头多远"的距离值 |
| `-cls` | Classification（图像分类） | 不定位，只给整张图一个类别标签，回到最基础的 [图像分类](/ai-yolo/cnn-basics) |
| `-pose` | Pose/Keypoints（姿态估计/关键点检测） | 输出人体关节点位置（肩膀、手肘、膝盖……），能判断姿态动作 |
| `-obb` | Oriented Detection（旋转框检测） | 跟普通 Detection 类似，但框能带角度旋转，不是只能水平/竖直摆放 |

**举个例子**：`yolo26n-obb.pt` 就是"nano 档位 + 旋转框检测"——无人机航拍场景很常用这一档，因为俯拍的车、船、建筑物往往是斜着的，普通水平矩形框会框进去一大圈多余背景，旋转框能贴着物体实际朝向去框，更精确。

### 每个变体都支持完整工作流

表格右侧 Training（训练）/ Validation（验证）/ Inference（推理）/ Export（导出）四列全部打勾，意思是这 35 个模型文件（7 任务 × 5 档位）不是"只有 Detection 能自己训练、其他任务只能用官方权重"这种阉割版——每一个都能自己训练、在验证集上评估、拿来推理、也能导出部署，命令行和 Python API 用法基本一致，只是换个 `model=` 文件名和对应的数据格式。

对无人机场景来说，**Detection（常规检测）+ OBB（旋转框）+ Depth（深度估计）** 大概率是最常用到的三个：识别地面目标、处理俯拍角度下物体的朝向、以及测距避障。

## Part 2：单张图片任务——YOLO26 各自升级了什么

**一句话理解**：Part 1 列了 YOLO26 的 7 种任务变体，但"YOLO26 比 YOLO11 强在哪"这件事，每个任务分到的"福利"并不一样——从完全没有专属升级，到只改了一个小细节，再到整个检测头被重新设计，力度依次递增。这一部分挑四个最有代表性的任务，按 YOLO26 给它的升级力度从小到大依次讲：**图像分类（无升级）→ 旋转框检测（小改动）→ 实例分割（结构性改动）→ 姿态估计（专属新技术）**。

### 图像分类（Classification）：这次 YOLO26 没有"开小灶"

先看升级力度最小的一个：翻遍源码，YOLO26 没有为分类任务单独设计新的检测头（Head），用的还是跟 YOLO11 一样的老结构。它享受到的唯一好处，是骨干网络（Backbone）本身变宽了——而这是 YOLO26 全系任务共享的通用升级，不是分类专属的。

这一点从官方给出的参数量对比看得很明显（nano 档位）：

| 版本 | 参数量 | 计算量（GFLOPs） |
|-|-|-|
| YOLO11n-cls | 1,633,584 | 0.5 |
| YOLO26n-cls | 2,812,104 | 0.5 |

参数量涨了 72%，计算量却完全没变。类比一下：这就像一个学生脑子里记住的知识点变多了（参数变多），但做题的思路、步骤没有变复杂（计算量不变）——单纯是"记性更好"，不是"解题方法升级"了。

真实用 `yolo26n-cls.pt` 对一张有人有车的照片做分类，输出的是"整张图最像哪一类"，不会告诉你物体在哪：

```
minibus（小巴）:       51.6%
police_van（警车）:    36.9%
trolleybus（无轨电车）:  9.6%
```

这也顺带说明了分类任务的本质局限——不关心"在哪、有几个、轮廓长什么样"，只关心"这张图整体上最像什么"，所以图里同时有人有车，模型也只能给一个笼统的答案。后面会看到，需要"定位"的任务（旋转框检测、实例分割、姿态估计），YOLO26 才会花心思专门升级；只需要"整体判断"的分类任务，升级就止步于骨干网络的通用红利。

### 旋转框检测（OBB）：把框的角度"松绑"

升级力度比分类高一档，但也只改了一处细节。普通检测框只能水平摆放，物体是斜着的（比如无人机俯拍一艘斜停的船）也只能用一个横平竖直的大框把它框进去，框里会带一大截多余背景；旋转框检测（OBB，Oriented Bounding Box）多预测一个"角度"，让框能跟着物体的朝向转一下，贴合得更紧。

预测这个角度，YOLO11 的做法是先算出一个数，再用 sigmoid 函数（一种能把任意数字压缩到 0~1 之间的函数）使劲把它"摁"进一个固定范围（大约 -45° 到 135°）里，相当于给角度强行加了道"栅栏"，不让它跑出这个范围。YOLO26 把这道栅栏拆掉了，直接输出原始角度数值，不做压缩。

为什么能拆掉？因为角度最终是通过三角函数（sin、cos）参与计算框的位置的，而 sin、cos 本身就是"转一圈又回到起点"的周期函数，天然不需要提前把数值摁进某个范围——加了栅栏反而可能让训练在栅栏边缘卡壳（数值越靠近边界，学习信号越弱，收敛越慢）。YOLO26 去掉这道多余的手续，角度预测能更自由地更新。真实下载的 `yolo26n-obb.pt`（nano 档位）参数量是 2,652,984 个，跟同档位其他任务规模相当，这个改动几乎不增加模型体积。

无人机航拍场景是旋转框检测用得最多的地方之一：停车场里的车、码头的船，俯拍视角下十有八九是斜着的，用旋转框才能框得准，不会带一圈多余背景。

### 实例分割（Instance Segmentation）：不但要框出来，还要描边

再往上一档，YOLO26 给的不只是一处小改动，而是两处结构性改进。普通目标检测（Detection）只给一个矩形框，告诉你"这个人在这个框里"；实例分割还要在框里进一步描出这个人的准确轮廓——哪些像素属于这个人、哪些是背景，就像拿画笔沿着人的身体边缘描一圈，而不是简单框一个方框。

Ultralytics 生成这个"轮廓"的办法，是先算出一组通用的"模板图"（Proto，可以理解成几十张抽象的黑白底图），再给每个检测到的目标算一组系数，用这组系数把模板加权拼出这个目标专属的轮廓——有点像调色：先准备好几十种基础色板，再告诉你"这个目标 = 30% 的色板 A + 50% 的色板 B + ……"，拼出最终颜色。

YOLO26 的分割头（源码里叫 `Segment26`）在"拼模板"这一步做了两个改进：

1. **看得更全面**：YOLO11 生成模板只用分辨率最高、但"视野"最小的那一层特征图（好比只拿着放大镜看局部细节）；YOLO26 会把范围更大、更抽象的另外两层特征图也融合进来一起生成模板，相当于放大镜之外又加了望远镜，细节和全局都看得到。
2. **额外找了个"陪练"**：训练时 YOLO26 会多算一个"整张图哪里是人、哪里不是"的辅助任务（不区分是第几个人，只看这片像素算不算人），跟"精确描边"这个正式任务一起训练，逼着网络学到更扎实的像素级特征——类似学生正式考试之外，多做了一份陪练卷，做完对成绩有帮助，但陪练卷本身不计入最终分数。这个"陪练"分支只在训练阶段存在，真机部署推理时会被直接砍掉，不多花一点点计算量。

真实用 `yolo26n-seg.pt`（nano 档位）跑一张有人有车的照片，检测到 5 个目标：

```
person: 置信度 0.919，轮廓蒙版尺寸 640×480（跟原图对齐）
bus:    置信度 0.895
person: 置信度 0.887
person: 置信度 0.866
```

每个目标除了框和置信度，还额外多了一张跟原图一样大的轮廓蒙版（Mask）——这就是分割比普通检测多输出的东西。

### 姿态估计（Pose Estimation）：YOLO26 的专属创新

四个任务里升级力度最大的一个。姿态估计在检测出"这是个人"的基础上，进一步输出这个人身上一串关键点（Keypoint，比如鼻子、肩膀、手肘、膝盖）的位置，从而判断出人的姿态动作。YOLO26 在这个任务上不只是套用全系通用的架构升级，还专门给姿态估计加了一整套新技术——**RLE（Residual Log-likelihood Estimation，残差对数似然估计）**。

#### 普通关键点回归 vs RLE

YOLO11 的姿态头（`Pose` 类）就是"预测每个关键点的 x, y 坐标，跟标注算距离当 loss"，默认所有关键点的误差都一视同仁地对待。YOLO26 的姿态头（`Pose26` 类）给每个关键点额外多预测一个"不确定性"（σ, sigma），还用一个叫 **RealNVP** 的归一化流模型（Normalizing Flow）去学"预测误差实际长什么形状"，而不是拍脑袋假设误差符合正态分布——训练时让模型自己说"这个点我有多不确定"。

对照两个类的源码（`ultralytics/nn/modules/head.py`）看得很清楚，`Pose26` 比 `Pose` 多了两样东西：

```python
class Pose26(Pose):
    def __init__(self, nc=80, kpt_shape=(17, 3), reg_max=16, end2end=False, ch=()):
        ...
        self.flow_model = RealNVP()          # 新增：归一化流模型
        self.cv4_kpts = nn.ModuleList(...)    # 关键点坐标分支
        self.cv4_sigma = nn.ModuleList(...)   # 新增：每个关键点的不确定性分支
```

对应的损失函数 `PoseLoss26`（`ultralytics/utils/loss.py`）训练时这么算：

```python
error = (pred_coords - gt_coords) / (pred_sigma + 1e-9)   # 归一化残差
log_phi = self.flow_model.log_prob(error)                  # 流模型算这个残差在"学出来的真实分布"下的概率
loss = log_sigma - log_phi + 惩罚项
```

RLE 是学术界 2021 年 ICCV 论文提出的技术，核心思路：YOLO 这种直接回归坐标的方法（跟传统基于热力图 Heatmap 的姿态估计不一样）在遮挡、模糊姿态上容易不稳，让网络自己学"这个点该多确定"，训练信号比单纯用坐标距离当 loss 更准。

#### 只花训练成本，不花推理成本

`cv4_sigma` 和 `flow_model` 只在训练（`self.training`）时参与计算，真实部署推理前会被 `fuse()` 直接砍掉：

```python
def fuse(self) -> None:
    super().fuse()
    self.cv4_kpts = self.cv4_sigma = self.flow_model = self.one2one_cv4_sigma = None
```

实际下载 `yolo26n-pose.pt` 跑一下，fuse 后参数量 **2,926,494**——跟没有这套机制的普通姿态模型体量相当。也就是说 RLE 是训练时的"外挂"，部署到无人机这种算力有限的设备上，推理速度、模型体积完全不受影响，白拿训练时学到的精度提升。

#### 真实跑一遍

```python
from ultralytics import YOLO

model = YOLO("yolo26n-pose.pt")
results = model("bus.jpg")
r = results[0]
kpts = r.keypoints   # xy: (人数, 17, 2)，conf: 每个关键点的置信度
```

真实输出（`bus.jpg` 上第一个人，COCO 17 个关键点里的前 5 个）：

```
鼻子   x=142.3 y=445.5 conf=0.990
左眼   x=149.2 y=436.8 conf=0.943
右眼   x=132.5 y=435.6 conf=0.997
左耳   x=153.0 y=441.9 conf=0.160   ← 明显偏低
右耳   x=108.7 y=438.6 conf=0.977
```

左耳这个点置信度只有 0.16（其他都在 0.9 以上），大概率是这个人侧身、左耳被挡住看不清——这正是 RLE 想解决的场景：天生就难判断的关键点，训练时能学出更大的不确定性，不会被硬按"跟其他清晰关键点一样"去算 loss，拖累整体训练效果。

#### 姿态模型也继承了 YOLO26 全系的通用升级

`yolo26-pose.yaml` 配置文件里还带着两个 [YOLO 架构](/ai-yolo/yolo-architecture) 笔记讲过的、YOLO26 全系共享的改动，不是姿态估计独有的：

- `end2end: True` → NMS-Free，姿态输出（框 + 关键点）也是端到端直接出结果，不需要再跑一遍 [NMS](/ai-yolo/object-detection-basics#非极大值抑制-non-maximum-suppression-nms) 去重
- `reg_max: 1` → 框回归不再用 DFL，直接回归坐标

## Part 3：训练自己的模型——先从数据标注开始

**一句话理解**：Part 1、Part 2 讲的都是官方预训练好的模型，直接拿来用。但如果你想识别一种官方数据集里没有的目标（比如无人机拍到的某种特定车辆、某种农作物病害），就要用自己的数据 Fine-tuning（微调，见[术语表](#fine-tuning-微调)）出一个专属模型——而微调开始之前，必须先有一份标好答案的数据，这一步叫**数据标注（Data Annotation / Labeling）**。

### 数据标注是什么

给原始数据（比如一张张图片）打上"标准答案"（标签，Label / Ground Truth）的过程——告诉模型"这张图里，这个位置是车，那个位置是人"。模型训练时就是拿自己的预测去跟这个标准答案比较、算差距（Loss），再照着差距调整自己，这就是[监督学习](/ai-yolo/dl-basics)的基本套路：没有标签这个"标准答案"，模型根本不知道自己错在哪，无从学起。

具体标注什么，跟 Part 2 里的任务变体一一对应：

| 任务 | 标注要打什么 |
|-|-|
| 分类（Classification） | 给整张图打一个类别标签，比如"这张图是 car" |
| 检测（Detection） | 给每个物体画一个矩形框 + 类别 |
| 实例分割（Segmentation） | 沿着物体轮廓描点，标出属于这个物体的每一个像素 |
| 姿态估计（Pose） | 在人体的每个关节点（鼻子、肩膀、膝盖……）上点一个点 |
| 旋转框检测（OBB） | 跟检测类似，但框要贴着物体朝向转一个角度 |

**举个例子**：YOLO 的检测标注文件长这样，一行代表一个物体：

```
0 0.523 0.481 0.216 0.312
```

依次是：类别编号、框中心点 x、框中心点 y、框的宽、框的高——后四个数全部归一化到 0~1（相对图片宽高的比例，不是像素值）。100 张图，平均每张 5 个目标，就要人工画 500 个框——这还只是最简单的检测任务，分割标注要沿轮廓描点，通常比画框慢 5~10 倍。

### 为什么它非常重要

1. **没有标注就没法训练**——监督学习的 Loss 是"预测值 vs 标签"算出来的，没有标签这个标准答案，模型无从学习。
2. **标注质量直接决定模型上限**——业内常说 Garbage in, garbage out（垃圾进，垃圾出）：框画得歪、该标的漏标了、同一类东西有的图标了有的没标，模型学到的就是这些错误和不一致，再好的模型架构也救不回来。
3. **往往是整个项目里最费时间的一步**——训练本身有 GPU 就能跑，标注却大多要靠人工一张张看；尤其无人机自己拍的特定场景（某种农作物病害、某型号车辆），网上没有现成数据集，标注工作量往往比调模型参数加起来还大。

### 标注工具推荐

| 工具 | 类型 | 支持的标注类型 | 适合的场景 |
|-|-|-|-|
| ⭐ **Label Studio**（目前在用） | 网页/自托管，开源免费 | 检测框、多边形、分割掩码、关键点、分类 | 支持多模态（图片/文本/音频/视频），以后要标的不只是图片时适合 |
| ⭐ **Roboflow**（目前在用） | 云端一站式平台，有免费额度 | 检测框、分割、分类 | 标注 + 数据集管理 + 训练 + 部署全部打通，新手最容易上手，YOLO 导出质量评测最好；注意免费版数据默认公开可见，敏感画面不建议用免费版 |
| **X-AnyLabeling** | 桌面软件，开源免费 | 检测框、分割、关键点、旋转框（DOTA 格式）、追踪 | 内置 SAM（Segment Anything Model）+ YOLO 模型做 AI 辅助自动标注，AI 先画个大概，人工只需微调修正，个人项目标注效率最高的路子之一 |
| **CVAT** | 网页/自托管，开源免费 | 检测框、多边形、折线、关键点（骨架）、立方体、视频插值 | 功能最全，支持自己搭在本地（Docker 一键起），无人机画面不想上传到别人服务器时选它；免费云端版（cvat.ai）有额度限制（10 个任务、500MB） |
| **Make Sense** | 纯浏览器网页 | 检测框、折线、关键点、多边形 | 不用注册、不用装软件，图片完全在本地处理不上传，标几十张图临时用一下最方便 |
| **TjMakeBot** | 纯浏览器网页，免费 | 检测框、多边形、旋转框（OBB）、关键点 | 几个工具里对旋转框支持最直接的，做无人机俯拍 OBB 标注可以重点看看 |

**怎么选**：优先用 AI 帮你标、人工只改错，选 **X-AnyLabeling**；无人机画面涉及隐私，选自托管的 **CVAT** 或本地运行的 **Make Sense**；就想标完直接接着训练、不折腾环境，选 **Roboflow**；专门标旋转框，选 **TjMakeBot** 或 **X-AnyLabeling**。这几个都能直接导出上面那种 YOLO 标注格式，标完可以直接拿去 `yolo train` 用。

目前实际在用的是 **Label Studio** 和 **Roboflow**（表格里标 ⭐ 的两行）——一个自托管、支持多模态，一个云端一站式带训练部署，两者搭配基本覆盖了"本地敏感数据自己标"和"标完直接接训练"两种场景。

## Part 4：目标追踪（Tracking）——从单帧到连续帧

**一句话理解**：Part 2 讲的分类、OBB、分割、姿态估计，处理的都是单独一帧静止图片，回答"这一帧里有什么、在哪"。目标追踪（Tracking）是在检测的基础上更进一步，把连续帧里同一个物体在不同帧的框关联起来，给它分配一个持续不变的编号（ID）——这样才知道"第 5 帧那个人"和"第 20 帧那个人"是不是同一个人，而不是每一帧都重新识别一遍、编号从头开始。

Ultralytics 内置了 6 种追踪器（Tracker），通过 `yolo track` 命令的 `tracker=` 参数指定：

```bash
yolo track model=yolo26n.pt source=video.mp4 tracker=bytetrack.yaml
```

| 追踪器 | `tracker=` | 特点 |
|-|-|-|
| ByteTrack | `bytetrack.yaml` | 最经典轻量方案，只用检测框位置做关联，不需要额外模型，速度最快 |
| BoT-SORT | `botsort.yaml` | ByteTrack 基础上加了相机运动补偿（GMC，Global Motion Compensation），可选打开外观特征（ReID，Re-Identification）辅助关联，更抗镜头晃动/遮挡 |
| TrackTrack | `tracktrack.yaml` | **当前默认追踪器**，同样支持 GMC + 可选 ReID |
| FastTracker | `fasttrack.yaml` | 专门做了"遮挡感知"（Occlusion-aware）处理——物体被挡住又重新出现时，能更好地保住原来的 ID，不会被当成新物体重新编号 |
| OC-SORT | `ocsort.yaml` | Observation-Centric SORT，纯运动轨迹关联，不依赖外观特征 |
| DeepOCSORT | `deepocsort.yaml` | OC-SORT + 外观特征（ReID），精度更高但更慢 |

**YOLO26 和 YOLO11 用法不一样的地方**：不加 `tracker=` 参数时 Ultralytics 会用默认追踪器——当前默认是 `tracktrack.yaml`；YOLO11 时代大家熟悉、网上大部分教程还在讲的默认值是 `botsort.yaml`。同样一行 `yolo track` 命令不显式指定 `tracker=` 的话，两个版本环境下实际追踪逻辑是不一样的，迁移旧教程代码时要注意。

`with_reid`（外观特征辅助关联）只有 `botsort` / `deepocsort` / `tracktrack` 三个支持打开：

```yaml
with_reid: True   # 开启后用外观特征（长相/颜色）辅助判断"这是不是同一个物体"，对遮挡后重新出现的场景更准，但要多算一个 ReID 模型，更慢
```

`bytetrack` / `ocsort` / `fasttrack` 三个纯靠运动/位置关联，不支持这个选项。

对无人机场景来说，追踪常用于持续锁定地面某个目标（车辆、人员）——即使这个目标每一帧的检测框位置有轻微抖动，追踪器也能保持同一个 ID 不丢，这是"目标跟随拍摄""持续监控同一目标"这类功能的基础。

## Part 5：部署上线——模型格式与 ROS2

**一句话理解**：前面几个 Part 讲的都是模型能做什么、精度好不好、怎么训练；这一部分讲最后一公里——训练好的模型，怎么真正跑到无人机的机载电脑上。训练出来的模型文件（`.pt`）就像手机拍出来的原始视频——画质最好、最方便剪辑，但不一定是最适合"播放"的格式。真要把视频发到某个设备上流畅播放，往往要先转码成那个设备认得、放得动的格式。模型部署也是同一个道理：训练用 `.pt`，但真要让它在某块特定芯片上跑得快，通常要转换成那块芯片认得的专属格式。

### 主流的模型格式有哪些

Ultralytics 目前支持导出 20 种格式（`model.export(format=...)`），挑几个用得最多、最该认识的：

| 格式 | 导出参数 | 好比什么 |
|-|-|-|
| PyTorch（原生 `.pt`） | 不用转 | 拍视频用的原始素材，方便改、方便训练，但"播放"（推理）效率不是最优 |
| ONNX | `onnx` | 一种"万能转换插头"——几乎所有推理工具都认识它，常被当成转成其他格式之前的中间站，而不是最终部署形态 |
| TensorRT | `engine` | NVIDIA 显卡的"专属定制西装"——特别合身（推理最快），但只能穿在量身定做的那台机器上，换一台电脑基本要重新定制一套 |
| OpenVINO | `openvino` | Intel 芯片（CPU/核显）的专属优化版本 |
| RKNN | `rknn` | 瑞芯微（Rockchip）芯片的专属格式——不少便宜的无人机机载电脑、飞控扩展板用的就是这颗芯片 |
| NCNN / MNN | `ncnn` / `mnn` | 腾讯、阿里做的"轻装上阵版"，专门给树莓派这类没有独立显卡、算力紧张的小设备用 |

**举个例子**：同一个 `yolo26n.pt`，之前实测导出成 ONNX 之后文件反而从 6.2MB 变成了 12.3MB——格式转换不等于"压缩变小"，每种格式是在"通用性、速度、体积、能在哪些硬件上跑"这几件事上做不同的取舍，没有哪个格式是全方位最优的，要看部署到什么设备上。

### 放到 ROS2 系统上一般用什么格式

分两个阶段，用的格式不一样：

**写代码、调试算法的阶段**：直接用 `.pt` 就够了。官方给的 ROS2 示例代码就是在节点（Node）初始化的时候加载一次模型，之后每次收到图像消息（Callback）直接拿来推理，不涉及任何格式转换，跑起来最省事：

```python
from ultralytics import YOLO

class YoloNode:
    def __init__(self):
        self.model = YOLO("yolo26m.pt")   # 只加载一次

    def image_callback(self, msg):
        results = self.model(msg)          # 每次收到图像直接推理
```

**真机部署到无人机/机器人上的阶段**：机载电脑上跑 ROS2 的场景，十有八九用的是 NVIDIA Jetson（Orin、Xavier 这类嵌入式显卡开发板），官方建议这时候换成 **TensorRT**（后缀 `.engine`）——"在 Jetson 上性能最好，是首选部署格式"这句话是 Ultralytics 官方文档原话。转换只要三行：

```python
from ultralytics import YOLO

model = YOLO("yolo26n.pt")
model.export(format="engine")     # 自动转成 .engine（内部会先转 ONNX 再转 TensorRT，不用自己操心中间步骤）
trt_model = YOLO("yolo26n.engine")
results = trt_model.predict(source="video.mp4")
```

有实测数据支撑这个选择：Jetson Orin NX 上用 FP16 精度的 TensorRT 跑 nano 模型，能达到 50Hz 左右；换成 ONNX Runtime 跑同样的模型，延迟明显更高，达不到无人机避障、跟踪这类要求"实时"的场景。

**有个坑一定要注意**：TensorRT 导出的 `.engine` 文件是跟硬件强绑定的——必须在无人机上那块 Jetson 本尊上导出，不能在开发用的笔记本电脑上转好了直接拷过去用；哪怕只是换一款 Jetson 型号，通常也得重新导出一遍。这跟 `.pt`／`.onnx` 那种"哪台电脑都能用"的格式是完全不同的使用方式。

如果机载电脑不是 NVIDIA 芯片（比如用瑞芯微方案的机载板），思路是先导出成 **ONNX** 这个通用中间格式，再用对应厂商的工具链转成设备专属格式——ONNX 在这里起的作用就是那个"万能转换插头"，一头接 PyTorch，另一头接各家厂商自己的芯片工具链。

## 术语表

### Backbone（骨干网络） {.ignore-header}

负责从原始图像里提取通用视觉特征（边缘、纹理、形状……）的那部分网络，是模型的共享地基。同一套 Backbone 换上不同的 Head 就能做检测、分割、姿态估计等不同任务——这也是 YOLO26 "一套骨干、七种任务"的由来。

---

### Head（检测头） {.ignore-header}

接在 Backbone 后面、专门负责把提取到的特征"翻译"成具体任务输出的那部分网络——检测头输出框，分割头（Segment）额外输出轮廓，姿态头（Pose）额外输出关键点。同一套 Backbone 换 Head 就能切换任务：Backbone 是"通才"，Head 是"专才"。

---

### Fine-tuning（微调） {.ignore-header}

拿一个已经在大数据集上训练好的模型（预训练模型，Pre-trained Model），换成自己的小数据集接着训练一段时间，让它"适应"具体任务，而不是从零开始训练——是迁移学习（Transfer Learning）最常用的具体做法。YOLO 里体现为 `model=yolo26n.pt`（带权重，微调）跟 `model=yolo26n.yaml`（只有架构，从零训练）的区别；`freeze=` 参数还能把 Backbone 前几层冻住（训练时不更新这些层），只微调后面的层，加快收敛、减少所需数据量。

---

### GMC（Global Motion Compensation，相机运动补偿） {.ignore-header}

追踪器里用来抵消"摄像机自己在动"造成的干扰的技术。比如无人机镜头轻微晃动，画面里所有物体看起来都在移动，GMC 先把这部分背景整体位移算出来抵消掉，只留下物体真正的运动，避免被误判成新目标。

---

### ReID（Re-Identification，重识别） {.ignore-header}

让追踪器不只看物体位置，还记住这个物体"长什么样"（颜色、纹理特征）的技术。物体被遮挡后重新出现时，能靠外观比对认出"这还是刚才那个"，而不是只靠位置去猜。代价是要多算一个外观特征模型，速度更慢。

---

### RLE（Residual Log-likelihood Estimation，残差对数似然估计） {.ignore-header}

YOLO26 姿态估计的专属技术：让模型在预测关键点坐标的同时，额外学一个"我对这个点有多不确定"（σ, sigma），并用 RealNVP 学出误差的真实分布，而不是默认误差都符合正态分布。只在训练时起作用，部署推理前会被砍掉，不增加推理成本，详见[姿态估计](#普通关键点回归-vs-rle)。

---

### RealNVP {.ignore-header}

一种归一化流模型（Normalizing Flow）——通过一串可逆的数学变换，把简单分布（比如正态分布）一步步"揉"成任意复杂的真实分布。RLE 用它来学习关键点预测误差的真实形状。

---

### Proto（原型/模板图） {.ignore-header}

实例分割里用来"拼"出轮廓的一组通用底图模板，每个检测目标只需要学一组系数，加权组合这些模板就能拼出自己专属的轮廓，不用给每个目标单独生成一整张轮廓图，省算力。YOLO26 的 `Proto26` 额外融合了多层特征、多算了一个训练期辅助任务，细节见[实例分割](#实例分割-instance-segmentation-不但要框出来-还要描边)。

---

### sigmoid 函数 {.ignore-header}

一种能把任意实数压缩到 0~1 之间的数学函数，S 形曲线，常用来把模型输出的"原始分数"转换成看起来像"概率"或"比例"的数值。YOLO11 的 OBB 头用它把角度预测挤压进固定范围，YOLO26 的 `OBB26` 取消了这一步。

---

### OBB（Oriented Bounding Box，旋转框） {.ignore-header}

比普通矩形框多一个"角度"参数的检测框，能贴着物体实际朝向摆放，不必永远水平/竖直——无人机俯拍场景（斜停的车、船）常用，能避免大矩形框里框进一堆多余背景。

---

### GFLOPs {.ignore-header}

Giga Floating Point Operations 的缩写，即"十亿次浮点运算"，衡量模型做一次推理要算多少次乘加运算的单位，数值越大代表越费算力。常跟参数量一起看：参数量涨但 GFLOPs 不变，说明模型是"变宽了"而不是"变复杂了"，[图像分类小节](#图像分类-classification-这次-yolo26-没有-开小灶)里 YOLO26 分类模型就是这种情况。

---

### ONNX {.ignore-header}

Open Neural Network Exchange 的缩写，一种跨框架的模型交换格式，几乎所有推理引擎都支持读取。常被当成"通用中间站"——PyTorch 模型先转成 ONNX，再进一步转成某个硬件专属的部署格式。

---

### TensorRT {.ignore-header}

NVIDIA 官方推出的、专为自家 GPU（包括 Jetson 系列嵌入式显卡）优化的推理加速格式，后缀 `.engine`。推理速度通常是几种格式里最快的，但导出的文件跟硬件强绑定，必须在目标设备上导出，换一款 GPU 型号基本要重新导出。

---

### OpenVINO {.ignore-header}

Intel 官方推出的推理加速工具链，专为 Intel 的 CPU、核显、VPU 优化，相当于 Intel 生态下的"TensorRT"。

---

### RKNN {.ignore-header}

瑞芯微（Rockchip）芯片专属的模型格式。不少低成本无人机机载电脑、飞控扩展板用的就是 Rockchip 芯片，这类设备上部署模型通常要转成 RKNN 格式，才能吃满芯片自带的 NPU 算力。

---

### NCNN / MNN {.ignore-header}

分别由腾讯（NCNN）、阿里巴巴（MNN）开源的轻量级推理框架，专为没有独立显卡、算力紧张的嵌入式设备（树莓派、手机）设计，追求体积小、依赖少，纯 CPU 也能跑得动。

---

### ROS2（Robot Operating System 2） {.ignore-header}

机器人/无人机领域最常用的软件开发框架，提供节点（Node）间通信、传感器数据管道等基础设施。一个"节点"通常对应一个独立运行的功能模块（比如"目标检测节点""飞控节点"），节点之间通过订阅/发布消息（触发 Callback）互相通信。

---

### Jetson {.ignore-header}

NVIDIA 推出的嵌入式 GPU 开发板系列（如 Orin、Xavier），体积小、功耗低，同时具备不错的 GPU 算力，是无人机、机器人机载电脑最常见的选择之一，也是 TensorRT 部署的典型目标硬件。

---

### FP16（半精度浮点数） {.ignore-header}

一种用 16 位（而不是标准 32 位，即 FP32）存储数字的方式，牺牲一点数值精度换取推理速度提升、显存占用减半。在算力有限的嵌入式设备（比如 Jetson）上，用 FP16 精度导出 TensorRT 模型是常见的加速手段，精度损失通常很小。
